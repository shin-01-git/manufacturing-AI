## 프롬프트 1 — 프로젝트 규칙 등록 + 4.9GB 원본 이해 (코드 작성 전 단계)

```
너는 동의대 제조 AI 과정 2팀(팀명: 문학적인 기계)의 프로젝트 "Factory Energy Copilot"을 함께 만든다.
아래 [프로젝트 규칙]을 .kiro/steering/project-rules.md 로 저장하고, 이후 모든 작업에서 지켜라.
그다음 [작업 1]만 수행하고 결과를 보고한 뒤 멈춰라. 모델·대시보드 코드는 아직 만들지 마라.

[프로젝트 목적·범위]
- 2025년 5월 공장 전체 전력량을 예측하고, 전기요금·탄소배출량으로 환산하며, 5초 원본의 이상 구간을 탐지해 근거 기반으로 보고하는 것을 목표로 한다.
- 이번 단계의 범위는 규칙 등록, 원본 구조·품질의 안전한 이해와 확인 결과 보고까지다. 산출물 생성·모델 학습·평가·에이전트·대시보드 구현은 후속 단계에서 한다.

[비목표]
- 이번 단계에서 예측 모델, 이상탐지 모델, 에이전트, Streamlit 화면, 분석 스크립트, 테스트 코드를 작성하거나 실행하지 않는다.
- 실시간 연동, 설비 제어, 고장 확정 진단, 생산량 대비 효율, 전년 대비 비교, 점검 이력 관리는 프로젝트 범위에 포함하지 않는다.

[데이터 사용 규칙]
- 원본 CSV는 읽기 전용으로 취급하며 어떤 방식으로도 수정·이동·이름 변경하지 않는다. 학습용과 검증용을 경로·변수·산출물에서 분리한다.
- 4.9GB 원본은 전체 메모리 적재, 에디터 열기, PowerShell Get-Content 전체 로드, Import-Csv 전체 로드, pandas read_csv 전체 로드를 금지한다. StreamReader 순차 스캔 또는 청크 처리만 허용한다.
- 점검·집계가 필요한 경우 청크 크기와 메모리 사용량을 기록하고, 한 청크를 처리한 뒤 원본 행을 보존하지 않고 해제한다. 메모리 제한을 넘을 가능성이 있으면 작업을 중단하고 방법을 재설계한다.

[발주처 요구사항 — 프로젝트 가이드]
1. 예측: 2025-05-10 00:00 ~ 2025-05-31 00:00, 1시간 단위 505개 시점의 공장 전체 전력량을 예측하고
   전기요금(180원/kWh)과 탄소배출량(0.424 kgCO2/kWh)으로 환산한다. 평가 지표는 MAE.
2. 이상치 탐지: 데이터에 일부러 삽입된 이상치를 머신러닝 기법으로 찾는다.
3. 에이전트: 예측·이상탐지 결과를 근거로 답하는 OpenAI API 기반 에이전트.
4. Streamlit 대시보드. 필수: 시간대별 전기요금·탄소배출량 예측 시각화, MAE, 이상치 탐지 결과(그래프 또는 알림),
   팀 이름/프로젝트 제목/간단 설명. 권장: 날짜 필터, 설비 필터, 예측치 기반 경고, 리포트 요약 박스.

[데이터 파일과 역할]
- data/training-datasets/rtu_data_full.csv : 학습용 5초 원본(2024-12 ~ 2025-04, 약 4.9GB). 학습·이상탐지에 사용.
- data/may-datasets/rtu_ground_truth_may.csv : 5월 정답. 컬럼 id, hourly_pow, may_bill, may_carbon, agg_pow.
  평가 코드에서만 읽는다.
- data/rtu_hourly.csv : 강의에서 받은 시간별 집계본(hour, module, n, activePower_mean, activePower_min,
  energy_Wh, voltage_mean, voltage_min, current_mean, powerFactor_mean, powerFactor_min). 교차검증용.
- data/rtu_sample_raw.csv : 5초 원본 일부(2025-04-01~02, 4개 설비). 빠른 실험용.

[실제 점검 대상 경로 매핑]
- 학습용 원본: data/rtu_data_full_훈련용.csv (위 논리 파일명 rtu_data_full.csv에 해당)
- 검증용 5월 정답: data/rtu_ground_truth_may_검증용(5월).csv (위 논리 파일명 rtu_ground_truth_may.csv에 해당)
- 이번 단계에서는 위 두 실제 경로만 안전하게 메타데이터·헤더·샘플·스트리밍 행 수 점검에 사용한다. 존재하지 않거나 확인하지 않은 보조 파일의 값은 사실로 기록하지 않는다.

[프로젝트 규칙]
R1. rtu_data_full.csv는 절대 한 번에 메모리에 올리지 않는다. DuckDB 또는 pandas chunksize로 처리하고,
    에디터로 열지 않는다. 원본은 수정하지 않는다. data/ 폴더와 .env는 .gitignore에 넣는다.
R2. 원본에서 만든 결과는 artifacts/ 아래 작은 파일(CSV/Parquet)로 저장한다.
    대시보드와 에이전트는 artifacts/ 만 읽는다(배포 시 원본을 올릴 수 없다).
R3. 시간 기준은 localtime(한국시간)만 쓴다. timestamp 컬럼은 KST와 맞지 않으므로 사용하지 않는다.
R4. 시간별 전력량 = Σ(activePower × 5/3600). 시간·설비별로 합한 뒤 설비 13개를 더해 공장 전체값을 만든다.
R5. 정답 파일은 학습·특성 생성·파라미터 선택·보정에 쓰지 않는다. 학습 코드가 정답 파일 경로를 참조하면 안 된다.
R6. 코드는 역할별로 나눈다: 집계(aggregate) / 학습(train) / 예측(predict) / 평가(evaluate) /
    이상탐지(anomaly) / 에이전트(agent) / 화면(app).
R7. 출력은 505개 시점, MAE는 504시간(마지막 2025-05-31 00:00 제외) 기준과 505개 기준을 둘 다 보고한다.
R8. 요금·탄소 환산은 정답 파일과 같은 척도를 쓴다: may_bill = hourly_pow × 180, may_carbon = hourly_pow × 0.424.
    (정답 파일은 1000으로 나누지 않았다. 환산 계수는 config 한 곳에만 두고, 화면에 계산식을 표기한다.)
R9. 고장 이력 데이터가 없다. 화면과 AI 문장 모두 "고장"이 아니라 "이상 구간/이상 징후"라고 쓴다.
R10. LLM은 숫자를 계산하지 않는다. 모든 수치는 Python이 계산한 artifacts에서 가져온다.
R11. OpenAI API 키는 환경변수 OPENAI_API_KEY(.env 또는 Streamlit secrets)로만 읽는다.
     코드·로그·커밋·스펙 문서에 키를 쓰지 않는다. 모델명은 환경변수 OPENAI_MODEL로 바꿀 수 있게 한다.
R12. 학습용 원본과 5월 검증 CSV는 파일 경로·변수·산출물·로그를 분리한다. 검증 CSV의 id·hourly_pow·may_bill·may_carbon·agg_pow는 학습, 특성 생성, 파라미터 선택, 보정, 이상탐지 기준 설정에 사용하지 않는다. 검증은 예측이 고정된 뒤 평가 단계에서만 수행한다.
R13. 4.9GB 원본을 처리할 때는 StreamReader 순차 처리 또는 제한된 청크만 사용한다. 행 수·청크 크기·처리 시간·오류·메모리 사용량을 로그에 남기고, 한 번에 원본 전체를 보유하지 않는다. 처리 중 임시 파일이 필요하면 data/ 밖에 만들고 완료 후 목록을 기록한다.
R14. 원본은 불변이다. 입력 파일의 Length와 LastWriteTime을 작업 전후 비교하고, 가능하면 해시도 비교한다. 원본과 중간 산출물을 덮어쓰지 않으며, 산출물은 artifacts/ 아래에만 저장한다.
R15. 모든 실행은 실행 시각, 코드·설정 버전, 입력 경로, 시간 기준, 청크 설정, 난수 시드, 결과 경로와 요약 통계를 기록해 재현 가능하게 한다. 확인하지 못한 값은 확정값처럼 쓰지 않고 "미확인/추정"으로 표시한다.
R16. 개인 식별정보와 비밀정보를 수집·출력·커밋하지 않는다. OPENAI_API_KEY 등 키·토큰·비밀번호는 환경변수 또는 시크릿 저장소에서만 읽고, 값·부분값·환경 덤프를 코드·로그·문서·화면에 남기지 않는다. 입력 데이터에 식별 가능 정보가 발견되면 값 대신 컬럼과 처리 방법만 기록한다.
R17. 코드 작성 전 단계의 종료 조건은 (1) 규칙 저장 지시, (2) 실제 두 CSV의 안전한 메타데이터·헤더·샘플·행 수 확인, (3) 확인 사실과 미확인 항목의 분리 보고, (4) 원본 불변 확인이다. 이 조건을 보고한 뒤 멈추고 사람의 확인을 기다린다.

[사람이 작은 파일로 미리 확인한 사실 — 전체 원본에서 맞는지 검증할 대상]
F1. rtu_hourly.csv: 2024-12-01 00시 ~ 2025-04-30 00시, 설비 13개, 3,601시간 × 13 = 46,813행, 결측·중복 없음.
    n=720이 46,800행, 마지막 시각(2025-04-30 00시)만 n=1.
    → 원본 예상 행 수는 약 33,696,013행(3,600시간 × 720 × 13 + 13).
F2. 샘플에서 Σ(activePower×5/3600)은 rtu_hourly.csv의 energy_Wh와 소수 4자리까지 일치.
F3. 공장 전체 시간별 전력량(완전한 3,600시간): 평균 39,129.4, 표준편차 95.8.
    월별 평균 39,125~39,133. 시간대·요일·설비 차이는 잡음 수준(설비별 평균 3,008.7~3,010.7), 자기상관 약 0.
F4. 5월 정답 hourly_pow: 평균 39,071.4, 표준편차 93.0. 시간대·요일 패턴 없음, 자기상관 약 0.
    학습 구간 평균보다 약 58(0.15%) 낮다. 이 차이는 학습 데이터의 추세로 설명되지 않는다.
F5. 샘플(4개 설비·2일)의 이상치는 5초 1행짜리 점 이상이다.
    - 전압: 3상 전압이 동시에 210V 미만(190~210). 13(3호기)에서만, 그 설비 행의 약 0.5%.
    - 역률: 3상 역률이 동시에 85% 미만(60~85). 15(예비건조기) 약 0.9%, 17(6호기) 약 1.1%.
    - rtu_hourly.csv의 voltage_min, powerFactor_min으로 보면 전 기간에서 위 3개 설비만 해당하고
      나머지 10개 설비는 voltage_min ≥ 210, powerFactor_min ≥ 85 이다.
    - 역률 이상 행은 activePower / Σ(V×I×PF/100) 비율이 정상(약 0.289)보다 높다(0.32~0.43).
    - 시간별 전력량에는 삽입 이상치가 보이지 않는다(설비 중앙값 대비 최대 편차 3.9%, 정규 잡음 범위).
F6. 샘플의 컬럼명은 module(equipment), localtime은 YYYYMMDDHHMMSS 숫자 14자리.
    정상 범위는 전압 210~220V, 전류 5~30A, 역률 85~100%, operation은 전부 1.

[작업 1] rtu_data_full.csv 이해와 검증 (코드 작성 전, 안전한 1회 순차 스캔으로 끝내라)
0) 먼저 두 실제 경로의 Length(바이트/GB)·LastWriteTime을 Get-Item으로 확인한다. 훈련 CSV가 실제로 4.9GB인지 십진 GB와 이진 GiB를 구분해 기록한다. 작업 전 값을 보존한다.
1) PowerShell Get-Content 전체 로드, Import-Csv 전체 로드, pandas read_csv 전체 로드를 하지 않는다. StreamReader의 앞부분 제한 읽기로 각 파일의 헤더와 처음 몇 줄만 확인하고, 훈련 CSV는 StreamReader 순차 스캔 또는 제한 청크로만 행 수를 센다. 검증 CSV도 동일한 방식으로 확인하되 전체 메모리 적재는 하지 않는다.
2) 컬럼명·컬럼 수·구분자·자료형 단서를 확인한다. 훈련 CSV의 첫 샘플에서 module(equipment), localtime(YYYYMMDDHHMMSS 숫자 14자리), timestamp, operation 및 계측 컬럼을 확인하고, 검증 CSV의 id·정답·agg_pow 구조를 확인한다. F1, F6과 다른 점을 표로 보여라.
3) 행 수는 헤더 제외 수와 산출 방법을 함께 기록한다. 물리 줄 수를 센 경우 CSV의 인용 줄바꿈을 별도로 파싱하지 않았다는 한계를 적고, 첫·마지막 샘플에서 기간 단서를 확인한다. 전수 확인하지 않은 기간·설비 목록·자료형은 미확인/추정으로 표시한다.
4) 안전한 스트리밍 점검으로 가능한 범위에서 결측 후보, (module, localtime) 중복 후보, 5초 간격 단절, operation≠1, accumActiveEnergy 감소, 시간·설비별 720행 미충족을 확인한다. 전체 전수 검증을 하지 못한 항목은 반드시 미확인으로 남기고, 샘플에서 보인 현상과 전수 결과를 구분한다.
5) 이번 단계에서는 분석 스크립트·애플리케이션 코드·테스트 코드와 parquet/CSV 분석 산출물을 작성하지 않는다. R4 집계, rtu_hourly.csv 비교, 공장 통계, 이상 행 전수 조사와 artifacts/hourly_from_full.parquet·artifacts/anomaly_rows.parquet 저장은 후속 구현 단계의 작업 목록으로만 기록한다.
6) 결과 보고 형식: ① 파일별 메타데이터·헤더·열 목록·행 수·기간/구조의 확인된 사실 ② F1~F6과 달랐던 점 ③ 결측·중복·간격·행 수 품질 점검의 확인 범위 ④ 미확인/추정 및 후속 확인 항목 ⑤ 판단이 필요한 질문. 확정값과 추측을 섞지 말고, 추측은 추측이라고 표시해라.
7) 끝나기 전에 두 원본의 Length·LastWriteTime을 다시 비교해 불변임을 확인하고, 원본·다른 파일을 수정하지 않았음을 보고해라. 단계 종료 조건을 충족하면 멈추고 내 확인을 기다려라.
```

## 원본 이해 확인 결과 — 프롬프트 1 사전 점검 기록

> 아래 값은 2026-10-10 기준으로 PowerShell `Get-Item`과 제한된 `StreamReader` 읽기로 확인한 기록이다. 두 CSV는 전체 메모리 적재하지 않았고, 분석 코드·산출물은 생성하지 않았다.

### 1) 파일 메타데이터와 4.9GB 여부

| 파일 | Length (바이트) | 십진 GB | 이진 GiB | LastWriteTime | 판정 |
|---|---:|---:|---:|---|---|

- S5 [Must] 에이전트 답변 숫자가 artifacts 값과 일치한다. S6 [Must] 가이드에서 확인된 필수 화면 요소 4가지가 모두 있다.
- S7 [Must] 원본 없이 artifacts만으로 대시보드가 실행된다.
  - acceptance: 위 S1~S7을 각각 테스트 명령·출력·산출물 경로에 연결하고 추적성 표에서 누락을 찾는다.
- 위험: 4.9GB 처리 중 메모리 초과·시간 초과, 물리 줄 수와 CSV 레코드 수 차이, 시간·설비 결측, 5월 분포 차이,
  이상탐지 규칙을 정답으로 해석하는 평가 편향, API 키/네트워크 실패, 미확인 PDF 요구사항, 5초 첫 화면 성능 저하다.
  각 위험의 영향·완화·잔여 위험·담당과 검증 방법을 문서화한다.
- [결정 필요] 두 기획서와 프로젝트 가이드의 본문·평가 기준이 이 문서의 확인된 요구사항과 충돌하는지 원문 확인 후 질문한다.
  특히 이상 영향의 정의·상태 경계값·규칙 결과의 평가 기준·D3 설비 13개 근거·D7 5초 측정 환경·예측구간 분위수·
  `Must/Should` 우선순위는 사용자 승인 전 확정하지 마라.

[Design 단계 — design.md: Requirements 승인 후에만 작성]
Requirements 승인 후에만 아래 설계를 작성하고, 요구사항을 새로 추가하거나 Tasks를 작성하지 마라.
- 시스템 경계와 비목표를 정의하고, 집계·전처리·학습·예측·평가·이상탐지·에이전트·API/function calling·Streamlit 앱·
  artifacts 저장소의 구성요소별 책임과 입력/출력을 분리해라.
- 데이터 흐름(원본 CSV → 제한 스트리밍/청크 → 작은 artifacts → 모델/평가/서비스)을 그려라. 4.9GB 원본을 전체 메모리에
  적재하지 않는 StreamReader 또는 제한 청크 처리 전략, 청크 크기·메모리·처리 시간·오류 로그와 원본 불변 검사
  (Length·LastWriteTime, 가능하면 해시)를 설계해라.
- 훈련·검증 경로·변수·산출물을 완전히 분리하고, 검증 CSV를 학습·특성 생성·파라미터 선택·보정·이상탐지 기준에
  사용하지 않는 누수 방지 경계와 자동 검사 위치를 설계해라. 예측 고정 후에만 평가가 정답을 읽도록 흐름을 고정해라.
- 모델·분석·예측·이상탐지 각각의 책임 경계와 baseline/model 선택, 5초 행 이벤트와 시간 집계의 관계, 규칙·통계·비지도
  방법 비교 및 평가 한계를 설계해라. 근거 없는 규칙을 정답으로 부르지 마라.
- API 계약(function schema, artifacts-only 경로, 숫자 출처, 키 없음/실패 fallback, 캐시·오류 응답), UI 계약(탭·필터·
  상태색·필수 그래프·경고·계산식·AI 문장 구분), 저장소/파일 계약(경로·필드·형식·버전·원본 불변)을 명시해라.
- 오류·관측성·보안·성능·재현성(실행 시각, 환경/코드/설정 버전, 입력 경로, KST, 청크, 난수 시드, 로그, 결과)을 설계해라.
  개인정보·비밀·OPENAI_API_KEY를 노출하지 않고, 배포 시 `data/`·`.env`·키를 포함하지 않는 가정을 검토해라.
- 첫 화면 성능 목표는 Requirements에서 근거·측정 환경·허용 오차를 승인받은 경우에만 수치 acceptance로 설계한다. 특히 `5초`가
  승인되지 않았다면 측정값을 기록하되 목표 대비 합격/실패로 판정하지 않는다. 캐시·데이터 크기·측정 명령과 실패 시 동작,
  API 네트워크 실패, 부분 산출물, 잘못된 스키마의 오류를 정의해라. 원본 없는 artifacts-only 실행과 배포/운영 가정, 복구·재실행·버전 호환성도 포함해라.
- 작업 1에서 확인한 CSV 헤더·크기·행 수는 사실로, 전수 미확인 항목과 PDF 미확인 내용은 미확인/질문으로 design.md에
  구분해 참조해라. 설계 검토 결과가 Requirements의 각 ID와 연결되는 추적성 표를 포함해야 한다.
- Design을 작성한 뒤 반드시 멈춰 사용자 승인을 받고, 승인 전 Tasks나 코드를 만들지 마라.

[Tasks 단계 — tasks.md: Design 승인 후에만 작성]
Design 승인 후에만 구현 가능한 작은 작업으로 분해해라. 각 작업은 `TASK-ID`, 선행관계, 대상 파일/모듈,
수행 내용, 산출물, 완료 조건, 검증 명령·테스트 전략을 반드시 가진다. 한 작업에 서로 다른 책임을 섞지 말고 다음 영역을
순서와 의존성으로 분리해라.
1. 데이터 탐색: 원본 메타데이터·스키마·품질 범위를 안전하게 확인하고 근거를 기록한다.
2. 전처리/집계: 제한 스트리밍으로 n=720 완전 시간과 artifacts/hourly_from_full.parquet을 만든다.
3. 학습: 세 베이스라인, 선형회귀, 트리 모델을 시간순 검증으로 비교하고 누수를 검사한다.
4. 검증/평가: 예측 505행, 504/505 MAE, 환산식, 총합 오차, 예측구간과 evaluation.json을 검증한다.
5. 이상탐지: 5초 행 기준 규칙·통계·비지도 모델, 방법 비교, anomaly 및 module status 산출물을 만든다.
6. 서비스화/에이전트: artifacts-only 도구 계약, function calling, 숫자 출처, 캐시와 fallback을 구현한다.
7. UI: Streamlit 탭·필터·상태색·필수 시각화·경고를 artifacts만으로 구현하고, 승인된 경우에만 승인된 첫 화면 성능 목표를 측정한다.
8. 문서화/운영: README·환경변수·재현 명령·로그·배포 목록·data/.env 제외·추적성·미결정 사항을 기록한다.
데이터 탐색/전처리/학습/검증/서비스화/UI/문서화 작업을 한 작업에 섞지 말고, 각 작업의 입력이 앞 작업의 승인된
산출물인지 명시해라. 원본 CSV는 읽기 전용이며, 모든 작업은 원본 Length·LastWriteTime 불변, train/validation 누수 방지,
개인정보·비밀 보호, 재현 가능한 명령과 로그, 검증 가능한 acceptance criteria를 지켜야 한다.

[추적성 표와 스펙 단계 종료 조건]
- 단계별 추적성 표는 공통 열 `요구사항 ID | 근거/우선순위 | 설계 결정/계약 | 작업 ID | acceptance/test | 산출물/근거`를 사용한다.
  Requirements에서는 설계·작업 칸을 `승인 후 작성` 또는 `미정`으로 두고, Design 승인 후 설계 결정/계약을 채우며,
  Tasks 승인 후 작업 ID와 검증 전략을 채운다. A1~A8, B1~B6, C1~C5, D1~D7, S1~S7과
  `REQ-PROB`, `REQ-GOAL`, `REQ-USER`, `REQ-SCOPE`, `REQ-NONSCOPE`, `REQ-SCENARIO`, `REQ-DATA`, `REQ-NFR`,
  `REQ-RISK`, `REQ-OPEN`을 모두 한 행 이상 연결하고, 연결되지 않은 요구사항·설계·작업이 없도록 종료 전에 검증한다.
- Requirements, Design, Tasks 문서가 각각 지정된 경로에 존재하고, 서로의 ID·계약·작업이 추적 가능하며, 핵심 미결정
  사항·질문과 승인 기록이 명시되어야 한다. 각 단계 보고에는 생성/수정 경로, 실제 실행한 각 검증 명령, 명령별 실제
  종료 코드(또는 종료 코드가 없는 경우 성공/실패 판정 근거), 핵심 출력 또는 실패 사유, 남은 위험을 포함해라. 검증
  명령을 실행하지 않았으면 해당 항목을 검증 완료로 보고하지 말고 `미검증`으로 남겨라.
- 사용자 승인 없이 다음 단계로 넘어가지 않고, 요구사항·설계·작업에 대한 사용자 승인 없이는 구현을 시작하지 않으며, 세 단계와 최종 승인이
  끝나기 전 애플리케이션 코드·데이터 분석 코드·학습 코드·테스트 코드·분석 산출물을 작성하거나 실행하지 않는다. 이 프롬프트를
  편집하는 현재 작업에서도 실제 `.kiro/specs/` 파일과 코드를 만들지 않는다.
- Git 저장소가 없는 환경에서는 `git init`, 커밋, 푸시를 하지 않는다. Git 검증이 실패하면 저장소 부재 사실만 기록하고
  저장소를 새로 만들지 마라. 원본 CSV와 PDF는 읽기만 하며 수정하지 않는다.
- 세 문서의 존재·상호 추적성·핵심 미결정 사항·Requirements/Design/Tasks 및 최종 사용자 승인 기록을 확인한 뒤에만
  스펙 단계를 종료한다. 마지막 조건은 사용자 승인이 없으면 구현을 시작하지 않는 것이다.
