# Requirements — 맞춤 정보 에이전트 (D 파트)

> 프로젝트: 2팀 「문학적인 기계」
> 서비스명: Factory Energy Copilot
> 담당 파트: D (맞춤 정보 · AI 에이전트)
> 사용 데이터: rtu_data_full.csv (원시, 기본), rtu_ground_truth_may.csv (검증)

## 0. 서비스 소개 (Factory Energy Copilot)
공장 13개 설비의 시간별 전력 데이터를 기반으로 사용량·비용·탄소배출량을 계산하고,
설비별 기준선에서 벗어난 이상 사용을 찾아 근거 중심의 AI 점검 리포트를 제공하는
에너지 운영 지원 서비스. 단순히 그래프를 보여주는 데 그치지 않고:
- 어떤 설비가 에너지를 많이 사용하는지 보여준다.
- 평소보다 얼마나 증가했는지 비교한다.
- 해당 이상이 비용·탄소배출량에 어떤 영향을 주는지 계산한다.
- 관리자가 무엇을 먼저 확인해야 하는지 AI가 정리한다.

중요 원칙: 현재 데이터만으로 설비 고장이나 생산 손실을 '확정'하지 않는다.
에너지 사용 패턴의 '이상 징후'와 '점검 우선순위'를 제공한다.

## 1. 개요 (D 파트 범위)
위 서비스에서 D는 '맞춤 정보 화면'과 'AI 점검 리포트'를 담당한다.
전력 데이터를 역할(설비/에너지 담당)에 맞게 보여주고, 검증된 수치를 바탕으로
AI가 점검 리포트를 생성한다. 수치 계산은 코드가, 설명·요약은 AI가 맡는다.
사용자가 자신에게 필요한 정보를 한눈에 보고, 자연어로 물어볼 수 있게 하는 것이 목적이다.

## 2. 용어 정의 (Glossary)
- 역할(Role): 대시보드 사용자의 직무 구분 (설비 관리 담당자 / 에너지 관리 담당자).
- 담당 설비: 특정 역할·사용자가 책임지는 설비 목록 (전체 13개 중 일부 또는 전체).
- 관심 지표: 역할별로 주로 보는 데이터 항목 (예: 전력, 역률, 요금, 탄소).
- 역할 기반 필터링: 선택한 역할에 따라 보여줄 데이터·화면을 거르는 것.
- 조회 함수: 데이터에서 필요한 값(설비·기간별 전력/요금/탄소/이상치 등)을 꺼내오는 함수.
- Function Calling: 사용자 질문을 보고 AI가 알맞은 조회 함수를 골라 호출하는 OpenAI 기능.
- 검증 파일(ground truth): 계산 결과가 맞는지 대조하는 정답 데이터(rtu_ground_truth_may.csv).

## 3. 사용자 역할 (User Roles / Personas)
### 역할 1 — 설비 관리 담당자 (47세)
- 간단한 엑셀은 하지만 복잡한 분석 화면은 부담. 한눈에 보이는 수치와 명확한
  상태 표시(정상/주의/이상)를 선호.
- 각 설비의 기간별 사용량 비교가 어렵고, 서서히 진행되는 역률 하락(노후화)을
  눈치채기 어렵다. 전력·전압·전류·역률을 함께 보기 어렵다.
- 현장 근무가 잦아 이상 설비명과 발생 시각을 먼저 확인. PC 기반 큰 화면·표를 선호.

### 역할 2 — 에너지 관리 담당자 (34세)
- 탄소 사용량과 전력 비용에 민감. 보고서 작성과 개선 효과를 중시.
- 여러 파일을 취합해 비용·탄소를 수동 계산. 월별 요금은 보지만 설비별 원인 파악이 어렵다.
- 회사 ESG 방침에 따라 탄소 배출 분석·감축 방안 모색. 전사 에너지·탄소 집계가 주 업무.
  경영진 보고용 요약 자료가 필요.

## 4. 범위 (Scope)
### 4-1. 포함 (In Scope) — D가 직접 만드는 것
- 작업자 역할·담당 설비 설정 (역할 기반 필터링)
- 역할에 맞는 맞춤 요약
- 자연어 질문응답 (OpenAI function calling)
- 데이터 조회 함수 (설비·기간별 값 조회)
- 화면 2개: ① 맞춤 정보 화면 ② AI 요약 보고서(상담) 화면

### 4-2. 제외 (Out of Scope) — 다른 파트 담당
- Streamlit 공통 UI 통합 → A
- 이상치 탐지 "모델" 자체(규칙/3σ·MAD/Isolation Forest) → C (D는 결과를 받아 활용)

### 4-3. 역할 변경 사항 (중요 — 팀 결정 반영)
- 당초 "공통 전처리·집계는 A가 전담"으로 가정했으나, 팀 논의 결과
  "각 파트가 필요한 전처리를 직접 수행"하는 방식으로 변경됨.
- 따라서 D도 원시 데이터(rtu_data_full.csv)에서 필요한 전처리·집계를 직접 수행한다.
  단, 전사 공통 집계가 아니라 'D 기능에 필요한 범위'만 집계한다.

## 5. 데이터 요구사항 (Data Requirements)
### 5-1. 입력 데이터
- 훈련용(학습) 데이터: training-dataset/rtu_data_full.csv
  (약 4.7GB 원시, 5초 간격, 설비 13개, 2024-12 ~ 2025-04)
  - 컬럼: module(equipment), timestamp, localtime, operation, 전압(R/S/T·선간),
    전류(R/S/T), activePower, 역률(R/S/T), reactivePowerLagging, accumActiveEnergy
- 검증용(정답) 데이터: may-dataset/rtu_ground_truth_may.csv
  (2025-05-10 00:00 ~ 05-31 00:00, 1시간 단위로 sum 된 정답)
  - 컬럼: id, hourly_pow, may_bill, may_carbon, agg_pow
  - 확인된 관계: may_bill = hourly_pow × 180, may_carbon = hourly_pow × 0.424
- 구조: training 데이터로 학습/계산 → may 데이터와 '비교(검증)'만 한다.
  (may 데이터는 정답이므로 학습에 쓰지 않는다.)

### 5-2. ⭐ 핵심 계산 공식 (전력량 환산 — 꼭 지킬 것)
- activePower는 '5초간의 평균 kW'(순간 세기)이지 누적량이 아니다.
- 전기요금·탄소는 kWh(누적량) 기준이므로, 먼저 kWh로 환산해야 한다.
  - 누적 전력량(kWh) = activePower × (5초 / 3600초)
  - 즉 5초 측정 1건당 kWh = activePower / 720
- 환산한 kWh를 (시간/설비별로) 합산한 뒤:
  - 전기요금(원)   = kWh 합계 × 180
  - 탄소배출(kgCO₂) = kWh 합계 × 0.424
- ⚠️ activePower를 그냥 더하면 틀린다. 반드시 kWh로 환산 후 합산한다.

### 5-3. 평가 지표
- MAE (Mean Absolute Error): 예측값과 실제값(ground_truth)의 절대 오차 평균.

### 5-4. 데이터 원칙
- 원본 파일을 수정하지 않는다 (읽기 전용).
- 데이터를 임의로 생성하지 않는다. 정해진 실제 데이터만 사용한다.
- D는 원시 데이터에서 'D 기능에 필요한 범위'를 직접 전처리·집계한다.
  전체를 빠짐없이 처리하고(청크), 이상치가 묻히지 않게 보존하며, 진행률을 남긴다.
- 요금·탄소 등 수치는 코드(pandas)가 계산하며, AI는 숫자를 생성하지 않는다.

## 6. 기능 요구사항 (Functional Requirements)
### FR-1. 작업자 역할·담당 설비 설정
- 사용자는 역할(설비/에너지 담당)을 선택할 수 있다.
- 역할에 따라 담당 설비와 관심 지표가 매핑되어 적용된다.

### FR-2. 맞춤 요약
- 선택한 역할에 맞는 정보(설비 상태/사용량 또는 비용/탄소)만 골라 요약해 보여준다.

### FR-3. 질문응답 (OpenAI function calling)
- 사용자가 자연어로 질문하면 AI가 알맞은 조회 함수를 호출해 데이터 기반으로 답한다.
- 숫자는 조회 함수(코드)가 반환하고, AI는 그 결과를 설명·요약만 한다.
- AI에게는 원본 CSV가 아니라, python이 계산·검증한 '요약 데이터'만 전달한다.

### FR-3a. AI 역할 1 — 현황 요약 보고서
- python이 계산한 검증 결과를 AI에 전달하면, AI는 아래 고정 형식으로 정리한다.
  1. 전체 에너지 현황
  2. 평소 대비 주요 변화
  3. 가장 주의할 설비
  4. 비용·탄소 영향
  5. 우선 확인할 현장 항목
  6. 분석의 한계

### FR-3b. AI 역할 2 — 이상 이벤트의 '사실 vs 추정' 구분
- AI는 이상 이벤트를 보고 '고장'이라고 단정하지 않는다. 관찰된 사실과 확인이
  필요한 사항을 구분해 서술한다.
- 예시: "15(예비건조기)의 22시 이후 사용량이 동일 시간대 기준보다 42% 높게
  4시간 지속되었습니다. 현재 데이터만으로 고장으로 판단할 수 없습니다. 먼저
  해당 시간대의 실제 가동 여부, 생산 작업 종료 여부, 대기 상태 전력 사용 여부를
  확인하고 전류·역률 변화와 계측 데이터 품질을 함께 점검하세요."

### FR-3c. AI 역할 3 — 역할별 다른 표현
- 같은 분석 결과를 사용자(역할)에 따라 다르게 표현한다.
  - 경영진용: 총 비용·증감·주요 위험을 5줄 이내로 요약
  - 에너지 관리자용: 설비 순위·비용 영향·기간 비교 중심
  - 현장 담당자용: 발생 시각·설비·점검 항목 중심

### FR-4. 화면 1 — 맞춤 정보
- 역할·담당 설비 설정 UI와, 그 역할에 맞는 사용량/예측/이상치 정보를 모아 보여준다.
- 계산 결과(수치)와 AI가 작성한 해석을 화면에서 시각적으로 구분해 표시한다.

### FR-5. 화면 2 — AI 요약 보고서 / 상담
- 질문 입력창과 AI 응답(요약·보고서 초안)을 보여준다.
- 모든 AI 답변에는 기준 기간과 데이터 품질 상태를 함께 표기한다.

## 7. 비기능 요구사항 (Non-Functional Requirements)
- 성능: D는 A가 집계한 가벼운 결과를 사용하므로 대용량 원시 처리 부담이 없다.
  (대용량 청크 처리는 A의 책임.)
- 신뢰성: 수치는 코드가 계산하고 ground_truth로 대조해 정확성을 확인한다.
- 보안: OpenAI API 키는 코드에 직접 쓰지 않고 secrets.toml(환경변수)로 관리하며
  .gitignore로 제외한다.
- 통합성: A의 공통 UI에 끼울 수 있도록 함수(부품) 형태로 제공한다.

### 7-1. AI 사용 제한 및 안전장치 (중요)
- AI는 energy_Wh, activePower_mean 등 수치를 새로 계산하지 않는다.
  (계산은 python/pandas, AI는 설명·요약만)
- AI가 원본 데이터에 없는 숫자를 지어내지 않도록, 검증된 요약값만 전달한다.
- AI가 "고장", "위험 확정" 같은 단정적 표현을 쓰지 않도록 프롬프트로 제한한다.
  (관찰된 사실과 확인 필요 사항을 구분해 서술)
- 모든 답변에 기준 기간과 데이터 품질 상태를 포함한다.
- 계산 결과와 AI가 작성한 해석을 화면에서 구분해 표시한다.
- OpenAI API 키는 하드코딩하지 않고 환경변수(secrets.toml)로 관리한다.

## 8. 제약 조건 (Constraints)
- 실행 환경: Python 3.14, Streamlit, pandas, openai (현 환경 기준).
- 팀 통합: A가 공통 UI를 통합 → D는 화면 함수(render)를 제공 (가 방식).
- 협업: GitHub 팀 저장소 사용.
- 전처리: 각 파트가 필요한 전처리를 직접 수행 (공통 전처리 전담 없음).
  D는 원시 데이터에서 D 기능에 필요한 집계를 직접 만든다.

## 9. 검증 기준 (Acceptance Criteria)
- kWh 환산(activePower × 5/3600) 후 합산한 전력량으로 요금·탄소를 계산한다.
- 환산 결과(요금·탄소)가 ground_truth(may-dataset)와 대조해 허용 오차(MAE) 내에 있다.
- 원시 데이터 집계 시 누적 처리 줄 수 = 실제 파일 줄 수 (전체 처리 증명).
- 역할을 바꾸면 보여지는 정보가 역할에 맞게 달라진다.
- AI 응답의 수치가 조회 함수 결과와 일치한다 (AI가 임의 수치를 만들지 않음).

## 11. 과제 '필수 포함 요소' (제출 기준)
- 시간대별 전기요금 및 탄소배출량 예측 시각화
- 정확도(MAE) 표시
- 이상치 탐지 결과 표시 (그래프 또는 알림)
