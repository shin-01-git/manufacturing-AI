# Design — 맞춤 정보 에이전트 (D 파트)

> requirements.md 의 요구사항을 어떻게 구현할지 설계

## 1. 설계 개요 (Overview)
D 파트는 공장 전력 데이터를 역할(설비/에너지 담당)에 맞게 보여주는 '맞춤 정보 화면'과,
자연어 질문에 데이터 기반으로 답하는 'AI 상담/보고서'를 제공한다.

핵심 설계 원칙은 **"계산은 코드, 설명만 AI"** 다.
- 모든 수치(전력량·요금·탄소·이상치)는 pandas 코드(d_queries.py)가 계산한다.
- AI(d_ai.py)는 그 숫자를 받아 '설명·요약'만 하며, 숫자를 새로 만들지 않는다.
- 데이터는 밖에서 인자(df)로 받는다. 조회 함수는 파일을 직접 읽지 않아 재사용·테스트가 쉽다.
- 원본 데이터는 수정하지 않고(읽기 전용), 임의 데이터를 생성하지 않는다.

전체 레이어: 원시 전처리(d_preprocess) → 집계본(d_aggregated.csv) → 조회 함수(d_queries)
→ AI 연동(d_ai) / 화면(d_screens). 역할 정의는 d_roles 에 둔다.

## 2. 아키텍처 (Architecture)
### 2-1. 전체 구조
A의 공통 Streamlit 대시보드에 D가 '화면 함수(부품)'를 끼워 넣는 구조(가 방식).
- D는 `render_header()`, `render_custom_info(df)`, `render_ai_report(df)` 세 함수를 제공한다.
- A는 이 함수들을 자신의 레이아웃 안에서 호출하기만 하면 된다.
- 화면 꾸미기(공통 UI 통합·스타일)는 A 담당, D는 기능 단위 함수를 넘긴다.

### 2-2. D 모듈 내부 구조
| 레이어 | 파일 | 역할 |
|---|---|---|
| 역할 정의 | `d_roles.py` | 역할(설비/에너지) 설정 + 요금·탄소 환산 계수(180, 0.424) |
| 전처리 | `d_preprocess.py` | 원시 4.57GB → 시간×설비 집계본 생성(청크 처리) |
| 조회 함수 | `d_queries.py` | 집계본에서 값 조회·계산(전력/전력량/요금/탄소/이상치/월별) |
| AI 연동 | `d_ai.py` | OpenAI function calling. 질문→함수 선택→설명 생성 |
| 화면 | `d_screens.py` | Streamlit 화면 2개(맞춤 정보 / AI 상담) |

데이터 흐름: `d_aggregated.csv` → `load_aggregated()` → df → (조회 함수 / AI / 화면).

## 3. 데이터 처리 설계 (Data Pipeline)

### 3-0. 전력 예측 시 참고할 주요 컬럼 (멘토 제시)
| 컬럼 | 의미 |
|---|---|
| activePower | 유효 전력. 순간적으로 설비가 소비하는 전력량(kW) |
| accumActiveEnergy | 누적 유효 전력량. 지금까지 누적 소비한 전력량(kWh) |
| operation | 가동 여부 (1 = 가동) |
| localtime | 시간 정보, 한국 시간 기준(문자열) |
| voltageR/S/T, currentR/S/T | 전압·전류 3상 값 |

### 3-1. 원시 데이터 처리 방식 (d_preprocess.py)
- training-dataset/rtu_data_full.csv(약 4.7GB)를 pandas 청크(100만 줄)로 전체 처리.
- 진행률을 d_preprocess_log.txt에 실시간 기록 (조각별 누적 줄 수).
- 원본은 읽기 전용. 임의 생성 없음.
- kWh 환산: activePower / 720 (= activePower × 5/3600)를 시간×설비별로 합산.

### 3-2. 집계 스펙 (d_aggregated.csv, 이상치 보존)
- 집계 단위: 시간(YYYYMMDDhh) × 설비(module)
- 보유 컬럼: kwh_sum, ap_mean, ap_min, ap_max, op_sum/op_ratio,
  energy_first/energy_last, 전압 3상(v{R,S,T}_mean/min/max),
  전류 3상(c{R,S,T}_mean/min/max), pf_mean, pf_min, n, bill(=kwh×180), carbon(=kwh×0.424)
- 이상치 보존: 전력 min/max, 역률 최저(pf_min)로 스파이크·저하 흔적 유지.

### 3-2b. 현재 집계본에 반영된 보강 항목 (멘토 기준 대비)
- operation → op_sum/op_ratio(가동 비율)로 반영됨.
- accumActiveEnergy → energy_first/energy_last로 반영됨(누적값 시작·끝).
- 전압·전류 3상(R/S/T) mean/min/max 반영됨(순간 피크 분석 가능).

### 3-3. 검증 방식
- 전체 처리 증명: 누적 처리 줄 수 == 집계 n 합계 (일치 확인 완료: 33,696,013).
- 요금·탄소 검증: 계산식 결과를 may-dataset(ground_truth)와 대조. → 10장 참조.

## 4. 역할 정의 및 매핑 (Role Mapping)

### 4-0. 전제 (중요)
- 데이터(rtu_data_full.csv)에는 "담당자 ↔ 설비" 구분 정보가 없다.
  따라서 담당자별로 특정 설비만 임의로 배정하지 않는다 (임의 생성 금지 원칙).
- 모든 역할은 기본적으로 설비 13개 전체를 대상으로 한다.
- 역할은 현재 2개(설비/에너지)만 다룬다. 필요 시 나중에 추가한다.
- 본 매핑은 추후 변경될 수 있다 (담당자-설비 구분 정보가 생기거나 요구가 바뀌면 반영).

### 4-1. 역할 목록
| 역할 ID | 이름 | 비고 |
|---|---|---|
| equipment_manager | 설비 관리 담당자 (47세) | 현장형, PC·표 선호 |
| energy_manager | 에너지 관리 담당자 (34세) | ESG·비용 민감, 보고서 중시 |

### 4-2. 역할별 매핑
| 항목 | 설비 관리 담당자 | 에너지 관리 담당자 |
|---|---|---|
| 담당 설비 | 전체 13개 | 전체 13개 (전사 집계 관점) |
| 관심 지표 | activePower(전력), 전압, 전류, 역률, operation(가동상태) | 전력량, 요금(=전력량×180), 탄소(=전력량×0.424) |
| 보는 단위 | 설비별 · 시간/기간별 | 전사 합계 · 월별/일별 추세 |
| 핵심 관심사 | 이상 설비명 + 발생 시각, 역률 하락(노후화) | 비용·탄소 규모, 상위 배출 설비, 감축 포인트 |
| 주로 보는 화면 | 설비 상태·이상 중심 | 비용·탄소 요약·보고서 중심 |
| 한 줄 요약 | "어느 설비가 언제 이상한가?" | "비용·탄소 얼마고 어떻게 줄이나?" |

### 4-3. 설비 목록 (13개, 집계본 실제 기준)
1(PM-3), 2(L-1전등), 3(분쇄기(2)), 4(분쇄기(1)), 5(좌측분전반),
11(우측분전반1), 12(4호기), 13(3호기), 14(2호기),
15(예비건조기), 16(호이스트), 17(6호기), 18(우측분전반2)
> 사용자는 '3호기', '호이스트'처럼 괄호 안 이름으로 부르므로, 조회 시
> resolve_equipment()가 이를 실제 설비명(예: 13(3호기))으로 매칭한다. (5장 참조)

## 5. 조회 함수 설계 (Query Functions, d_queries.py)
공통 규칙: 첫 인자 df는 집계본 DataFrame. df가 None이면 "데이터 없음"을 돌려준다(멈추지 않음).
기간 인자(start/end)는 집계본 hour 키(YYYYMMDDhh 문자열) 기준으로 거른다.

| 함수 | 하는 일 | 반환 핵심 |
|---|---|---|
| `load_aggregated()` | 집계본 CSV 로드 | DataFrame 또는 None |
| `resolve_equipment(df, name)` | '3호기'→'13(3호기)' 등 설비명 매칭 | (정확한_설비명 또는 None, 후보목록) |
| `get_equipment_power(df, eq, s, e)` | 특정 설비 전력/전압/전류/역률/가동률 | ap_mean/min/max, pf_min, 피크 등 |
| `get_equipment_energy(df, eq, s, e)` | 특정 설비 전력량+요금+탄소 | energy, bill, carbon |
| `get_total_energy(df, s, e)` | 전체 전력량+요금+탄소 | energy, bill, carbon, 설비수 |
| `get_anomalies(df, s, e)` | 역률 저하(pf_min<70) 구간 | 설비명·시각·역률값 목록 |
| `detect_power_anomalies(df, s, e)` | 전력 3σ 이상치 | 설비·시각·전력·평소평균·배수·방향 |
| `rank_carbon_by_equipment(df, s, e, top)` | 설비별 탄소 배출 순위 | 상위 설비·탄소·요금 |
| `monthly_compare(df, eq)` | 월별 전력량/요금/탄소+전월 대비 증감 | 월별 items |
| `get_data_overview(df)` | 기간·설비수·행수·이상치/역률저하 건수 | 데이터 품질 상태 사실 |
| `equipment_status_board(df, s, e)` | 설비 13개 정상/주의/이상 판정 | 신호등 목록 |
| `summarize_for_role(df, role, s, e)` | 역할별 한줄 요약 | title, lines |

설비명 매칭: `resolve_equipment`는 ① 완전 일치 ② 괄호 안 별명/앞 번호 일치
③ 부분 포함 후보 순으로 찾는다. 후보가 2개 이상이면 모호로 보고 되묻게 한다.

## 6. AI 연동 설계 (OpenAI Function Calling, d_ai.py)

### 6-1. 등록된 함수 목록 (TOOLS, 8개)
AI가 질문을 보고 호출할 수 있는 도구. 실제 구현은 d_queries.py.
- get_equipment_power : 특정 설비 전력(전압·전류·역률·가동률 포함)
- get_equipment_energy : 특정 설비 전력량 + 요금·탄소
- get_total_energy : 전체 전력량 + 요금·탄소 (에너지 담당용)
- get_anomalies : 역률 저하 구간(설비명·시각·역률값) — 역률/노후화 질문용
- rank_carbon_by_equipment : 설비별 탄소 배출 순위 (감축 대상 선정용)
- get_data_overview : 기간·설비수·행수·이상치/역률저하 건수 (데이터 품질 상태)
- detect_power_anomalies : 전력 3σ 이상치 (이상 설비/시각)
- monthly_compare : 월별 전력량/요금/탄소 + 전월 대비 증감

### 6-2. 호출 흐름
1. 사용자가 자연어로 질문 ("3호기 전력 얼마야?", "3월 현황 보고서 써줘")
2. ask()가 질문을 보고 모드 자동 판단: 단순 조회(qa) / 종합 보고서(summary)
3. 코드가 '데이터 품질 상태'(get_data_overview)를 미리 조회해 AI에 제공
   (보고서 모드면 '가장 주의할 설비'(전력 이상치)도 질문 기간 기준으로 미리 제공)
4. AI가 알맞은 도구를 선택 → 코드가 숫자를 계산해 반환 (여러 번 반복 가능)
5. AI는 그 숫자를 받아 설명·요약만 생성 (숫자 생성 금지)
- 전제: AI에게는 원본 CSV가 아니라 코드가 계산·검증한 '요약 데이터'만 전달.

### 6-3. 질문 모드 자동 분기 (A안)
- decide_mode(): 질문에 '보고서/요약/현황/정리/리포트/점검' 등이 있으면 summary,
  아니면 qa.
- qa : 질문한 값만 2~4문장으로 간결하게. 안 물은 항목(설비 이상 등) 억지로 안 채움.
- summary : 6단계 보고서(아래) 형식. 필요한 도구를 여러 개 호출해 종합.

### 6-4. 질문 기간 자동 인식
- _extract_period_from_question(): "1월", "2025년 3월", "2025-02" 같은 표현을 읽어
  집계본 기간(YYYYMMDDhh)으로 변환. 연도가 없으면 집계본에 그 달이 있는 해를 찾아 맞춘다.
- 이 기간을 '주의할 설비' 미리 조회에 적용 → 맞춤 정보 화면과 같은 기간 기준이 되어
  두 화면의 결과가 일치한다. (월 표현이 없으면 전체 기간)

### 6-5. AI 역할 설계 (프롬프트로 제어)
- 역할 1 — 현황 요약(summary): 6단계 고정 형식
  (전체 현황 / 평소 대비 변화 / 주의 설비 / 비용·탄소 영향 / 현장 확인 항목 / 분석의 한계)
- 역할 2 — 사실/추정 구분: 이상 이벤트를 '고장'으로 단정하지 않고,
  관찰된 사실과 확인 필요 사항을 구분해 서술.
- 역할 3 — 역할별 표현: 에너지 관리자용(설비 순위·비용·기간 비교) /
  설비 관리 담당자용(발생 시각·설비·점검 항목)으로 다르게 표현.

### 6-6. 신뢰성 원칙 / 안전장치 (프롬프트 + 코드로 강제)
- AI는 수치를 새로 계산하지 않는다. 도구가 준 값만 사용.
- 결과(items)에 값이 있으면 "확인할 수 없다"고 하지 않는다. 기간 밖일 때만 '없음'을 밝힌다.
- 질문한 값(특정 달·설비)을 답 맨 앞에 먼저 제시한다.
- 설비명은 '3호기'처럼 불러도 코드가 실제 설비명으로 매칭. 모호하면 후보를 되묻는다.
- 단위 고정: 전력 kW, 전력량 kWh, 요금 원, 탄소 kgCO₂, 전압 V, 전류 A.
  AI가 임의로 1000배 환산하지 않는다.
- "고장", "위험 확정" 등 단정적 표현 금지.
- 모든 답변 끝에 '데이터 품질 상태'(기간·설비수·행수·이상치/역률저하 건수) 포함.
  이 값은 코드가 미리 조회해 넣으므로 질문 종류와 무관하게 항상 표기된다.
- 계산 결과(숫자)와 AI 해석을 화면에서 구분 표시(화면의 '근거' 확장 영역).

### 6-7. API 키 관리
- 키는 하드코딩하지 않고 .streamlit/secrets.toml(OPENAI_API_KEY)로 관리.
- secrets.toml은 .gitignore로 깃 추적 제외. 코드는 st.secrets["OPENAI_API_KEY"]로 읽음.
- 키가 없으면 ask()는 'no_api_key' 상태만 돌려주고 멈추지 않는다(맞춤 정보 탭은 그대로 사용 가능).

## 7. 화면 설계 (UI, d_screens.py)
### 7-1. 화면 1 — 맞춤 정보 `render_custom_info(df)`
- 역할 선택 + 날짜(시작/종료) + 설비 필터.
- 역할별 핵심 요약 박스(큰 숫자 카드).
- 설비 담당: 설비 13개 신호등(정상/주의/이상) + 전력 3σ 이상치 표 +
  설비 선택 시 전력/전압/역률/전류 추이 그래프(이상 시점 강조).
- 에너지 담당: 총 전력량·요금·탄소 + 탄소 상위 설비 막대 + 월별 전월 대비 비교.

### 7-2. 화면 2 — AI 상담 `render_ai_report(df)`
- 역할 선택 + 질문 입력 + '질문하기' 버튼.
- 답변(AI 해석)과 '📊 계산 결과(코드가 조회한 숫자 — 근거)'를 구분 표시.
- 키 없으면 안내 메시지, 키 있으면 d_ai.ask() 호출.

### 7-3. A 공통 UI와의 연동 (함수 인터페이스)
- A는 render_header() / render_custom_info(df) / render_ai_report(df)를 호출.
- df를 안 넘기면 각 함수가 내부에서 집계본을 자동 로드(_load_df, @st.cache_data).

## 8. 팀 인터페이스 (A/B/C 연동)
- A(공통 UI): 위 render 함수 3개를 제공받아 자신의 레이아웃에 배치.
- C(이상치 모델): D는 자체 3σ 규칙으로 '관찰 사실'을 보여주되, C의 결과가 오면
  목록/구간 형태로 받아 화면·AI 근거로 활용 가능(인터페이스는 추후 합의).
- B(예측): 예측 결과를 받으면 화면에 표시 가능(받는 형태 추후 합의).

## 10. 검증 결과 (MAE)
- 요금·탄소 환산식을 ground_truth(may-dataset, 505개 행, 2025-05-10~05-31)와 대조.
- 결과: 요금 MAE 0원, 탄소 MAE 0 kgCO₂ (완전 일치).
  → 계산식(요금=kWh×180, 탄소=kWh×0.424)이 정답과 일치함을 확인.
- 한계: 5월 원시 데이터가 없어 '원시→집계' 전체 파이프라인의 MAE는 미검증.
  본 검증은 요구사항에 명시된 환산 관계(may_bill=hourly_pow×180 등)를 확인한 것.

## 11. 미결정 사항 (Open Design Questions)
- B(예측)·C(이상치) 결과를 D 화면에서 받을 때의 데이터 형태(값/파일/함수) 합의 필요.
- 역할별 담당 설비를 전체로 둘지, 사용자가 일부만 선택하게 할지.
- '분쇄기'처럼 후보가 여러 개인 설비명을 화면에서도 되묻게 할지(현재는 AI 상담만 되물음).
